# 001 — `applied_at` is a DATE, not a timestamp

**Status:** Accepted · 2026-09-11
**Affects:** `Jobs.applied_at`, `db/pool.ts`, `JobTable.tsx`

## Context

`applied_at` is filled by an `<input type="date">`. The user picks a calendar
day and never enters a time — the browser submits `"2026-09-04"`, nothing more.

Migration 003 converted the column to `TIMESTAMPTZ` along with `created_at`,
`updated_at`, and `status_changed_at`, for consistency. `TIMESTAMPTZ` requires a
time and an offset, so Postgres supplied the missing parts: midnight, in the
session timezone (UTC on Neon). Every row became `2026-09-04T00:00:00Z`.

That fabricated midnight is what broke. A value pinned to UTC midnight renders
as the *previous evening* anywhere west of UTC, so a job applied to on Sept 4
displayed as Sept 3 for users in the Americas. The date the user typed and the
date shown back to them no longer matched.

Three separate layers turned out to be inventing a time-of-day, each one
independently capable of shifting the day:

| Layer | What it did |
|---|---|
| Postgres (003) | `AT TIME ZONE 'UTC'` pinned each date to UTC midnight |
| `pg` driver | Parsed `DATE` into a JS `Date` at the *server process's* local midnight |
| Browser | `new Date("2026-09-04")` is UTC midnight per the JS spec; `toLocaleDateString()` then shifted it |

The driver and browser layers were invisible locally, because the API server and
the browser shared a timezone and their errors cancelled out. They would have
reappeared on deploy, where Render runs UTC and the browser does not.

## Decision

Store `applied_at` as `DATE`, and keep it a plain `"YYYY-MM-DD"` string all the
way to the screen.

- **Migration 004** converts the column, with `USING (applied_at AT TIME ZONE
  'UTC')::date` — the explicit inverse of what 003 did. The timezone is named
  rather than left to the session, so the file produces the same result no
  matter who runs it or from where.
- **`pool.ts`** registers a type parser for OID 1082 so `pg` hands back the raw
  string instead of constructing a `Date`.
- **`JobTable.tsx`** formats from the string (`split("-")`), never through a
  `Date`. `Date` is used only for the "applied within 7 days" subtraction, where
  both operands are millisecond counts and no timezone is involved.

`created_at`, `updated_at`, and `status_changed_at` stay `TIMESTAMPTZ`. They are
real instants generated by `now()`, so a timezone is meaningful for them and
per-viewer conversion is correct behaviour, not a bug.

## Alternatives rejected

**Pin a non-UTC timezone at the DB or session level.** Postgres will happily
interpret input in `America/Los_Angeles` instead of UTC, which makes the display
correct for one region. It assumes every user lives in that region, and breaks
the moment someone travels or signs up from elsewhere. It also only fixes the
write side; the browser still converts on read.

**Correct the offset in the frontend.** Adding hours back before display hides
the symptom at one call site. Every other place that reads the value needs the
same correction, and the correction itself is wrong under DST and outside the
assumed timezone.

**Go back to `TIMESTAMP` (no time zone).** This looked safe because it was what
the column was before 003 and no bug was visible. It was not safe — it worked
only because no conversion happened on either end locally. The fabricated
`00:00:00` is still there, and whether it survives depends on which layer
appends a `Z` during serialization.

## Consequences

- The value is timezone-proof by construction. There is no time-of-day for any
  layer to reinterpret, so server location and user location stop mattering.
- Frontend date code got smaller, not larger — no `Date` construction, no
  locale formatting, no correction logic.
- The API response now mixes two shapes on purpose: `"applied_at": "2026-09-04"`
  next to `"created_at": "2026-09-04T22:24:51.902Z"`. This asymmetry is the
  point. The urge to make them uniform is what produced 003.
- Anything comparing `applied_at` against a `TIMESTAMPTZ` column must cast
  deliberately — Postgres will coerce silently otherwise and quietly pull the
  session timezone back in. The follow-up query compares dates on both sides
  (`now()::date - status_changed_at::date`) for this reason.
- `DATE` cannot hold a time, so if applications ever need one (an exact
  submission timestamp, say), that is a new column, not a widening of this one.

## The rule this generalizes to

Pick the type by asking whether the value *has* the information, not whether the
information is currently useful:

> Does this value mean the same thing to a viewer in another timezone?

Yes — it is one instant on the timeline — use `TIMESTAMPTZ`. No — it is a square
on a calendar — use `DATE`. A type that requires information the value does not
have will have that information invented, and invented values corrupt real ones.
